Earlier today (`7419c3b`) the audio was moved to one AudioContext per page with steps scheduled on the audio clock 100 ms ahead. The owner then reported it **still glitches when lots of notes are entered quickly — "jumping like a CD", sound "kinda slow motion"**. That is now fixed in **`7b62fa4`, pushed to `main` and live** (verified by content on kid-sequencer.web.app: `pulseNoteBlock`, `SCHED_START_S`, `_pulseScaleNow` in index.html; `will-change: transform`, `beatBadge::before` in `styles.css?v=92`). **Root cause: not the audio engine** (0 underruns in every run) **but the main thread.** Per-step visuals — each sounding note's swell (two forced layouts + four custom-property writes per note per step; `var()` keyframes can't run on the compositor) and the beat-badge flash (animating `background`/`box-shadow` = a main-thread repaint every frame) — kept the thread so busy that, on a slower device, the `setTimeout` tick ran up to ~500 ms late, past the 100 ms of audio queued, so steps played late or were dropped. Found by building a headless-Chrome CDP harness with CPU throttling as an iPad stand-in (saved in `docs/handover/perf-harness/`, uncommitted): tapping 8 notes/s at 3× throttle went from 10–11 late + 2–10 dropped steps per 6 s to **0 / 0**; at 4× from 6–19 + 17–36 to 0–3 + 0–5; a packed grid at 4× from 10–20 + 11–30 to 0–3 + 0; disabling every CSS animation alone took 4× playback load from 93 % to 17 %. The fix is four parts: swell via Web Animations with cached literal keyframes; `.noteBlock { will-change: transform }`; beat flash animates only `opacity` of two pseudo-elements; audio lead 100 → 300 ms (first step still 100 ms ahead so Play answers at once; lessons stay at 100 ms). **Nothing has been tried on an iPad or in Safari** — the CPU throttle is only a proxy and main-thread load at 4× throttle is still ~95 %, so the margin on a genuinely slow device is unknown. CLAUDE.md's audio section was updated (committed in `7b62fa4`).

## Decisions & Rationale

- **Debugged from evidence, not by guessing.** The first hypotheses (audio-thread overload, WebKit node accumulation, AudioParam event build-up, DOM-interaction crackle bug 255949) could not be reproduced or confirmed on desktop and were not acted on. The reproducible failure was a main-thread stall: simulated 150 ms stalls at 160 bpm gave 15 late + 3 dropped steps, 250 ms gave 23 dropped (100 ms lead). That pointed at what was starving the thread.
- **Each part was A/B-tested alone and none was enough alone.** WAAPI swell alone: no improvement (96–98 % busy). `will-change` alone: barely. 300 ms lead alone: fewer drops but lateness still 400–600 ms. Combined (WAAPI + `will-change`): the big drop. The beat flash was worst single animation family (alone: 54 % busy at 4× vs 17 % floor).
- **Rejected: `latencyHint: "playback"`.** WebKit has no latencyHint support (bug 214258, NEW as of its last update in 2021 — I could not verify current Safari), so it would be a no-op on the very device that matters.
- **Rejected: adaptive lead.** A fixed 300 ms is simpler and measured sufficient; the restart/re-anchor logic and the "clock crawling" threshold (3×lead + step) all key off `SCHED_LEAD_S` already.
- **Rejected: gating the fix on the owner's iPad result first** — the harness showed a real, quantified main-thread problem independent of the device.
- **Kept the old class-based swell path** (`setBlockPulseVars`, `.noteBlock.playing`, `@keyframes swell`) as the fallback where `Element.animate` is missing (iOS < 13.4). Not dead code.
- **Committed only the audio hunk of CLAUDE.md.** The 9-line "Session Handover" pointer block links to untracked `docs/handover/`, so it stays unstaged (same as last session). Staged by `git apply --cached` of a truncated patch, since `git add -p` isn't available here.

## Landmines

- **Never judge rendering/animation cost in the Browser pane.** Its compositor is frozen: forced layout costs 30–45 ms even idle and `getAnimations()` shows ~127 phantom animations. All real numbers came from headless Chrome over CDP (see the harness README).
- **Anything that animates on every step or note must be compositor-only** — `transform`/`opacity`, literal keyframe values (not `var()`), no forced layout. A main-thread repaint per step is an audio bug on a slow device. Don't revert the beat flash to `background`/`box-shadow`, don't put `var()` back in the swell keyframes, don't drop `will-change: transform` from `.noteBlock`.
- **`_pulseScale`/`_pulseKF` are declared up near `_triggeredNotes` (~line 840), not beside `pulseNoteBlock`** — `buildGrid()` resets `_pulseScale` and runs before the function's code does (TDZ). `_pulseScale` is re-measured once per `buildGrid()`; anything that changes the stage scale without a layout pass would leave stale swell sizes (resize/orientation both go through `layoutPass` → `buildGrid`, so currently fine).
- **The audio lead is 300 ms by design.** A note placed < 300 ms ahead of the playhead waits for the next pass; lessons keep 100 ms (`SCHED_LEAD_S = LESSON ? SCHED_START_S : 0.300`). The debug panel's `min lead`/`worst tick late` skip the ~200 ms after a restart (`statsFromW`) because the timer deliberately runs early then.
- **The resync after a restart is measured from the tick's start (`nowW`), not its end.** The end-of-tick version left a 3.5–6 ms standing grid offset (pre-existing since `7419c3b`); now 0.5 ms. Don't "simplify" it back.
- **`will-change: transform` on every `.noteBlock`** adds a standing layer per note (≤128). If the iPad shows memory pressure/tab reloads, reconsider before anything else.
- **Harness gotcha:** `shot.mjs` once saw 0 beat badges loading the bare `/` while a clean probe of the same URL rendered 128 cells — a script timing artifact, not an app bug. Use `index.html` in scripts.
- **`?audiodebug=1` is sticky in `localStorage` on the owner's iPad** — a green panel stays over the bottom of the screen (kids will see it) until `/?audiodebug=0` is opened. Tell the owner.
- **Every `play*` voice must read `_audioNow()`, never `audioCtx.currentTime + …`**, and a new voice must call `trackNode()` (Stop = `liveNodes` → `stopAllAudioNow()`; an untracked future-scheduled node would now sound up to 300 ms after Stop). All ~20 current source creations were checked: only the silent warm-up buffer isn't tracked.
- **`public/js/volume-fader.js` and `public/index-works.html` are orphan old copies** — the live fader is inline in `index.html`.
- `node serve.js` is still running on `:3000` from an earlier session; it serves the working tree.
- Still true from before: **a push to `main` IS a production deploy**; `printMarkInsets()` varies slightly with viewport size (compare in the SAME run — it matched before/after this fix at 0.07449/0.20951/0.95223/0.8224); `.claude/skills/handover-*` exist only locally; the stray untracked `git` file at the repo root predates these sessions and is left alone; the bash-guard false-positive notes in CLAUDE.md still apply (used `git commit -F <file>` and relative git commands this session).
